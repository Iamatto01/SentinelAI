# Executive Summary  External Penetration Test

## Overall Security Posture: **Failing  Critical Remediation Required Before Continued Production Use**
The platform is not currently defensible against a motivated external attacker. Testing identified 61 findings  2 Critical, 8 
High, 30 Medium, 13 Low, and 8 Informational  and, more importantly, several of those findings combine into a chain 
that leads from an unauthenticated internet connection to full application and likely infrastructure compromise. The two 
Critical findings are not isolated defects; they are symptoms of a legacy stack that has been running without a coherent 
patch, hardening, or secure-development discipline for a long time. The most damning evidence is not any single 
vulnerability, but the platform's baseline: PHP 5.4 (end-of-life since December 2018, unpatched for approximately 95 
months), Apache 2.4.6 with 120 applicable CVEs (25 critical, 51 high), and OpenSSL 1.0.2k with 48 applicable CVEs 
including 19 high-severity. This is a known-vulnerable operating stack exposed to the public internet, and the application-
layer findings sit on top of it.
## The Most Material Risks, in Business Terms
**First, the platform is leaking its own secrets.** An exposed `secrets.json` configuration file was retrieved without 
authentication. Any credential, API key, signing secret, or database connection string inside it must be treated as 
compromised  not "potentially exposed," but *known to an external party during this engagement*. If those secrets are 
shared across other IIUM services (a common pattern in institutional deployments), the blast radius extends beyond this 
host.
**Second, the data layer is directly injectable.** A SQL injection vulnerability was confirmed, and separately, `/api/login` 
was bypassed via NoSQL injection. Either finding alone is sufficient to read, modify, or destroy application data, and 
combined with the exposed secrets, an attacker does not need to brute-force anything  they can read the credentials 
and walk in.
**Third, access control is not reliably enforced.** `GET /api/v1/documents/1` returned data without authentication, and the 
ID is a sequential integer. That is the classic BOLA/IDOR pattern: if document 1 is readable, documents 2 through N 
almost certainly are too. In an academic platform, "documents" is likely to mean student records, submissions, or 
examination material  so the business impact is not abstract confidentiality loss, it is a probable personal-data breach 
under Malaysian PDPA obligations, with the notification and regulatory exposure that implies.
**Fourth, the file upload path is exploitable toward remote code execution.** Two separate upload endpoints (`/api/file` and 
`/upload`) accepted PHP content disguised as an image, including the double-extension variant. Combined with a web 
server that executes PHP and runs a nine-year-old interpreter, uploading a PHP payload and requesting it back is a 
practical, low-skill path to remote code execution on the host.
## The Attack Chain
These findings are not independent; they compose into a straightforward, sequential compromise:

1. **Reconnaissance is trivially successful.** Certificate Transparency subdomain discovery, whatweb/httpx fingerprinting, 
and the version audit together disclosed the full stack: PHP 5.4, Apache 2.4.6, OpenSSL 1.0.2k, and a Moodle instance 
running with version deliberately obscured. An attacker now knows exactly which public exploits to fetch.
2. **Credential and secret acquisition.** The exposed `secrets.json` yields application secrets; the SQL injection yields 
database contents; the NoSQL `/api/login` bypass yields an authenticated session without any credential at all. The 
attacker now has three independent routes to authenticated context.
3. **Lateral access to data.** With an authenticated session in hand, the IDOR on `/api/v1/documents/{id}` permits 
sequential enumeration of other users' records  a horizontal privilege escalation at scale.
4. **Code execution.** The upload endpoints accept PHP payloads with bypassed Content-Type validation and double 
extensions. The uploaded webshell is served by the web server and executed by PHP 5.4.
The end state is remote code execution on a production educational platform, achieved without any zero-day and without 
any credential theft from a user. Every step of that chain used findings that *should* have been individually blocked by 
basic controls: authentication on API resources, server-side file type validation, parameterized queries, and a supported 
runtime.
## Systemic Issues
Two systemic failures underpin the individual findings and are more consequential than any single item:
**Authentication and authorization are inconsistently applied across the API surface, not just missing in one place.** The 
combination of an unauthenticated `/api/v1/documents/{id}`, a NoSQL authentication bypass on `/api/login`, and an 
exposed secrets file indicates that authentication is treated as a per-endpoint implementation detail rather than a platform-
wide enforcement layer. Fixing the single IDOR endpoint without addressing this will relocate the problem, not solve it. 
Separately, the Login Rate Limiting Test and the API Rate Limiting Test results belong in the same conversation  if 
authentication can be bypassed and also isn't rate-limited, credential-based defenses are effectively absent.
**The underlying stack is out of support and cannot be made secure through application-level patching.** PHP 5.4 
reached end-of-life in December 2018; Apache 2.4.6 carries 120 applicable CVEs; OpenSSL 1.0.2k carries 48. No amount 
of code review on the application layer removes those CVEs. The TLS/SSL audit and Cryptographic Failures findings 
(OWASP A04:2025) sit on this same foundation. The Moodle instance being "version obscured" is a defensive measure 
that removes the attacker's convenience but not their capability  security through obscurity is not remediating an 
unverified CVE exposure.
Supporting this, the missing security headers, the DNS posture findings (SPF/DMARC/DKIM), and the Security Logging 
and Alerting Failures (A09) category indicate that security monitoring is not currently capable of detecting the sort of multi-
step intrusion described above  which means the platform may already have been compromised in ways this blackbox 
assessment cannot observe.
## Remediation Priority: What to Fix First, and Why
**Immediate (within 2472 hours, before anything else):**
1. **Rotate every secret in `secrets.json`** and remove the file from the web root. Assume the contents are public. This is 
the single highest-leverage action because it invalidates the attacker's easiest path.
2. **Take the file upload endpoints offline or restrict them behind authentication with server-side content inspection.** The 
RCE chain is the most severe achievable outcome; removing the upload surface breaks it.
3. **Patch the SQL injection and the NoSQL authentication bypass on `/api/login`.** Parameterized queries for the former; 
server-side type enforcement and operator blacklisting (reject `$ne`, `$gt`, `$regex` in auth payloads) for the latter.
4. **Enforce authentication on all `/api/v1/*` resources**, then re-run the BOLA probe against sequential IDs to verify.
5. **Isolate and begin the PHP 5.4 ! supported version migration, and patch or replace Apache 2.4.6 and OpenSSL 
1.0.2k.** This is listed in the immediate tier because it is the root cause of the largest CVE count and cannot be deferred 
 but it is realistically weeks of work, so begin the planning and interim compensating controls (a WAF in front of the host, 
restrictive network egress, aggressive monitoring) *now* while the migration proceeds.
**Short-term (within 30 days):** enforce authorization consistently as a middleware layer rather than per-endpoint; add 
rate limiting to `/api/login` and all API endpoints; deploy the missing security headers; implement SPF/DMARC/DKIM 
correctly; and enable centralized logging with alerting on authentication failures, upload events, and anomalous API 
access patterns.
**Remediation sequencing matters here.** Rotating secrets and disabling the upload endpoints *first* breaks the known 
attack chain; patching individual findings in the order they appear in the findings report does not. A remediation plan that 
begins with Medium-severity items will leave the Critical chain intact while appearing to make progress.
## Recommendation: **Reject Risk Acceptance  Mandatory Remediation**

The risks identified are not acceptable for a production educational platform, and I recommend the institution formally 
reject risk acceptance and require remediation before continued external exposure. The Critical findings position an 
attacker at the doorstep of remote code execution and a probable personal-data breach, and the underlying stack is out of 
support in a way that means the platform's *unpatched* state is not a temporary condition  it will worsen over time. 
Beyond technical risk, the exposed secrets and the plausibly enumerable document API create direct regulatory exposure 
under PDPA and material reputational exposure for an academic institution holding student records.
**Interim recommendation:** if the immediate fixes cannot be implemented within the stated window, place the platform 
behind authenticated access only (disabling anonymous reachability entirely), add a WAF with rules for upload validation 
and injection signatures, and accelerate the platform migration. These are compensating controls, not fixes  the 
systemic authentication inconsistency, the injectable data layer, and the unsupported runtime must still be remediated. I 
recommend a re-test focused on the Critical and High findings within 30 days of remediation to confirm both that the 
original chain is broken and that no equivalent paths remain open.

2. Methodology
This assessment was performed using the SentinelAI Autonomous Pentest Platform, an automated security testing 
platform that orchestrates multiple scanning modules covering network, web application, and configuration security. 
Findings are deduplicated by root cause and assigned an evidence-validation tier. AI review is advisory and is not 
treated as proof of exploitability. Methodology follows OWASP Testing Guide v4.2 and NIST SP 800-115.

ports, running services, and outdated software versions.
